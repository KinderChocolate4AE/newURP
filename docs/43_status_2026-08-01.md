## 1. 이번 캠페인의 실제 궤적

### 1단계 · 진단과 방향 재설정

시작 시점 상태: C-1 인증 캠페인 종료, **양성 결과 0**, 서로 충돌하는 두 핸드오프.
핵심 문제는 *"clean crossing = 0 이 몇 달째"* 였는데, 원인을 파 보니
**`clean_crossed = threshold AND NOT boxed_in`** — 즉 **포위(containment)를 실패로 채점**하고
있었습니다. 지표 정의가 결과를 지우고 있던 것입니다.

방향 결정 세 가지:

| 결정 | 내용 |
|---|---|
| 공격자 먼저 | 방어자를 붙잡고 있어봐야 상대가 고정이면 강건성 주장을 못 한다 |
| **비손실 격추 프레이밍** | "몇 대가 필요한가"는 net 없이 들이받아도 되므로 논문이 안 된다. **위협-유도 조향 + 비손실 포획**이 개념 기여 |
| 모드 전환 | net capture ↔ hard kill 을 **이산 상태기 없이** 중재하는 완결된 시스템 |

### 2단계 · 시스템 구축 (M4)

동결 파일(`env.py` 등)을 한 줄도 안 건드리고 래퍼·프록시로 얹었습니다.

```
make_train_env      동결 env (물리 · 종료)
ModeSystemEnv       하드킬 방아쇠 · no-kinetic zone · M4 보상
attach_attacker     공격자 사다리 A1-A3 주입 (백엔드 프록시)
spawn_for_episode   초기조건 랜덤화
attach_threat_obs   위협 등급 관측
```

- **공격자 사다리 A1→A3** — A1 은 동결 공격자에 *문자 그대로 위임*, A2 지그재그·편대 라우팅, A3 발사 유도(베이팅). λ(손실회피)를 1급 축으로 승격.
- **임무 5분할 라벨** — NET_CAPTURE / CAPTURE_WITH_CONTACT / HARD_KILL / PENETRATED / SPENT_FAIL / TRUNCATED. 프로젝트 최초의 **임무 레벨 지표**.
- **2층 지표** — 1차 무력화율, 2차 비손실 비율.
- **`w_kill` sweep 축** — 값을 고르지 않고 **뒤집히는 지점이 결과**가 되도록 설계.

이 단계의 첫 양성 신호: oracle 에서 **ring 이 무접촉으로 `n_worst1` = 6–10, hold 는 0**.

### (3) 명제 N 의 운용 버전 — 이론 절이 됨

```

w < ρ : 조향 없이도 포획된다 (조향의 방어가치 = 0)
w > ρ : 조향이 필요하다
```

## 3. 깨진 전제 셋 + 버그 하나 (이번 달의 실질)

### 붕괴 ① τ 를 grounding 하니 조향이 불필요해졌다

`tau_deploy = 0.4` 를 폐로 기하로 다시 풀면 0.15 가 나옵니다. 그러자 게이트에서
**무개입(hold)이 12/12 를 전부 저지** — 조향 문제가 사라졌습니다.
명제 N 이 정확히 예측한 결과였습니다 (`w = ½·78·0.15² = 0.88 < ρ = 2.0`).

> **"협력 조향이 필요하다"는 논문 전제가 근거 없던 `τ = 0.4` 위에 서 있었던 것입니다.**

**해소**: τ 를 under-modeling 했던 것 — 커밋-포획 지연은 비행시간 하나가 아닙니다.
분해(§2-(2))로 0.30 이 되고 전제가 복원됩니다.

### 붕괴 ② 콘의 축방향 밴드가 τ 와 어긋나 있었다

`cone.range_max = 29.847` 인데 τ_flight 동안 네트가 실제로 가는 거리는 **8.22 m** 입니다.
**네트가 닿을 수 없는 15 m 표적을 "포획"으로 판정**하고 있었습니다. 3.6배 어긋남.
τ 선언의 필연적 귀결이라 연동 수정했습니다 (`half_angle` 도 함께).

### ★ 버그 · 베이스라인이 공짜 하드킬을 쓰고 있었다

```
params.py:  scripted.limiter_pressure = 1.0   "RESERVED -- env receives-and-ignores"
docs/29:    M4 가 limiter Box(4) idx3 을 **커밋 비트**로 재사용
=> 스크립트 베이스라인이 1스텝째에 전 limiter 하드킬 커밋 (n_committed=4 실측)
=> hold/ring/intercept 가 bit-identical 이 되어 게이트가 무의미한 값을 재고 있었다
```

**못 잡았으면 논문의 모든 baseline 이 무의미했고, 50런 스윕 뒤에 발견했을 겁니다.**

### 붕괴 ③ `kill_radius` 를 grounding 하니 limiter 조향 능력이 붕괴 — **미해소**

베이스라인 버그를 고치고 paired **n=48** 로 확정:

```
hold   PENETRATED 35 / NET_CAPTURE 9 / SPENT_FAIL 4    침투 0.729   접촉 0.00
ring   동일                                             침투 0.729   접촉 0.38
paired: ring 이 이긴 에피소드 0, 진 에피소드 0, 동일 48
```

**스크립트 조향이 임무 결과를 하나도 바꾸지 않습니다.** (n=12 에서 오가던 ±0.17 은 노이즈였습니다.)

원인: **`kill_radius` 가 물리적으로 다른 두 양을 겸하고 있습니다.**

| | 물리량 | 옳은 값 |
|---|---|---|
| (1) | 치사·접촉 반경 | **0.75 m** — grounding 이 맞음 |
| (2) | 공격자가 존중해야 하는 이격 | limiter 의 **τ_kill 내 도달집합** |

공격자가 피하는 반경 = `repel_margin × lam_range × kill_radius` = **0.75 m** 로 묶여 있는데,
실제로 피해야 하는 것은 limiter 의 몸통이 아니라 도달집합입니다:

```
r_avoid = kill_radius + ½·a_lim·τ_kill² + v_lim·τ_kill = 0.75 + 0.17 + 3.00 = 3.92 m
```

**기존 2.0 보다 오히려 큽니다.** τ 때와 **같은 종류의 과소 모델링**이고,
유도가 `env_sys` 의 하드킬 마진식 안에 이미 있습니다.

## 7. PPT 구성 제안

2–3 장이면 이 구성을 권합니다.

**1장 · 무엇을 만들었나** — 시스템 스택 그림 + 2층 지표 + 산출물 규모(코드/테스트/문서 숫자).

**2장 · 문헌 앵커링과 그 결과** — 앵커 표(Xu/Pliska) + **전제가 세 번 깨졌고 세 번 다 학습 전에 잡혔다** + 명제 N 위상 경계 그림(a\*=39.3 을 브래킷이 가로지름).

**3장 · 현재 위치와 다음** — 막힌 것 1개(치사/회피 분리) + 학습 일정 + 경쟁 논문 대비 차별점 4축.

### 자르는 지점에 대한 의견

**"실제 물리 파라미터 앵커 직전까지"로 자르는 것은 권하지 않습니다.**
그렇게 자르면 한 달 요약이 *"인프라를 많이 만들었고 결과는 없다"* 가 되는데,
그건 이 캠페인 시작 때 스스로 지적하신 바로 그 상태입니다.

**앵커링을 오히려 중심에 놓는 것을 권합니다.** 이유:

1. 앵커링이 **외부 검증이 붙은 유일한 부분**입니다 (Xu 원문 역산이 논문 표와 정확히 일치, Pliska 실측 비율).
2. **전제가 세 번 깨진 것이 이번 달의 실질적 연구 성과**입니다 — 그것도 전부 계산 자원을 쓰기 *전에*, 사전등록된 게이트가 잡았습니다. 방법론적으로 자랑할 일이지 숨길 일이 아닙니다.
3. 학습 결과가 없는 이유를 **변명이 아니라 결과로** 설명할 수 있게 됩니다: *"근거 없는 파라미터 위에서 돌리면 50런이 낭비였을 것이고, 실제로 그 조건에서는 조향 이득이 0 이었다"*.
4. 다음 달 계획이 자동으로 명확해집니다 (결정 1개 → 게이트 → 학습).

다만 발표 톤은 조심해야 합니다. **"세 번 실패했다"가 아니라 "게이트가 세 번 작동했다"** 로 말해야 하고,
학습 착수 날짜를 명시해서 "그래서 언제 결과가 나오나"에 미리 답해야 합니다.

만약 말씀하신 뜻이 *"C-2(FPV 스펙시트)로 실제 기체 스펙을 넣는 단계 직전까지"* 였다면,
그건 **좋은 절단면입니다** — 문헌 앵커링(Xu/Pliska)은 이미 다 들어가고, 다음 챕터가
