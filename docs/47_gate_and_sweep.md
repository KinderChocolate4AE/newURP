## 1. 게이트 확장 (`op_gate.py`)

임무 결과만 보면 "조향 이득 0" 으로 읽히지만, `docs/46` 이 보였듯 그건 **두 개의
반대 효과가 상쇄된 결과**다. 게이트가 이제 둘을 따로 낸다.

```
채널 (i)  도달집합 차단   Δv_shot = v_shot(limiter 있음) - v_shot(limiter 제거), 같은 seed
채널 (ii) 조준 파괴       psi · omega_req = v_perp/d
판정식    hold 대비 최선 v_shot 과 평균 v_shot 을 **둘 다** 개선해야 순이득
```

### 1.1 채널 분해 결과 (A2 공격자 · 위협 랜덤화 · n=12)

| 배치 | 채널(i) Δv_shot | 최선 v_shot | 평균 v_shot | v⊥ 중앙 | ω>ω_max | ψ 중앙 |
|---|---:|---:|---:|---:|---:|---:|
| hold | 0.00007 | 0.6581 | 0.3444 | 3.06 | 0.0% | 6.0° |
| ring | 0.00095 | 0.6741 | 0.3370 | 2.94 | 0.0% | 6.1° |
| intercept | −0.00109 | 0.6581 | 0.3451 | 3.06 | 0.0% | 6.1° |

```
ring      vs hold : 최선 +0.0159  평균 -0.0074  -> ★ 순이득 없음
intercept vs hold : 최선 +0.0000  평균 +0.0007  -> ★ 순이득 없음
```

**A1 과 A2 에서 실패 기전이 다르다** — 이것이 이번에 새로 보인 것이다:

| 공격자 | limiter 가 v⊥ 에 하는 일 | ω 구속 | 지배 채널 |
|---|---|---:|---|
| A1 (직진) | 0.44 → 7.27 m/s **를 만든다** | 44.8% | **(ii) 조준 파괴** |
| A2 (지그재그) | 3.06 → 2.94, 사실상 무변화 | 0.0% | **(i) 이 애초에 없다** |

A2 는 공격자 스스로 이미 v⊥ ≈ 3 을 싣고 다니므로 limiter 가 더할 것이 없고, 그
사거리대에서는 slew 도 구속하지 않는다. **어느 쪽에서도 협력의 순이득이 없되,
이유가 서로 다르다.** 선언 판정식이 이 둘을 같은 방식으로 걸러냈다.

## 2. ★ 정정 5 — 게이트 판정이 부풀린 지표를 쓰고 있었다

`docs/40 §8.2` 는 `interdiction_rate = 1 − PENETRATED` 가 SPENT_FAIL(탄 소진·미무력화)
과 TRUNCATED 를 성공으로 세므로 부풀려진다고 이미 적었고, `mission_eval` 은 그래서
분해해서 낸다. **게이트만 옛 정의를 쓰고 있었다.**

```
[위협 고정 · n=24]
  hold       PENETRATED 21 / SPENT_FAIL 3    무력화 0.00   (옛 '저지' 0.12)
  ring       PENETRATED 19 / SPENT_FAIL 5    무력화 0.00   (옛 '저지' 0.21)
  intercept  PENETRATED 21 / SPENT_FAIL 3    무력화 0.00   (옛 '저지' 0.12)

  조향 이득 = +0.00 무력화 기준  /  +0.08 옛 기준
  >> ★ 게이트 실패 (옛 정의로는 '통과'였다 -- SPENT_FAIL 을 성공으로 세던 부풀림)

[위협 랜덤화 · n=24]
  세 배치 모두 PENETRATED 18 / NET_CAPTURE 5 / SPENT_FAIL 1  -> 무력화 0.21 동일
  >> ★ 게이트 실패: 조향이 무의미하다
```

**세 배치 전부 포획 0 인데 "조향 이득 +0.08" 로 통과 판정이 나오고 있었다.**
정정 방향은 게이트를 **더 엄격하게** 만드는 쪽이므로 선언 위험이 없다.
옛 값도 함께 찍어 과거 기록과 대조 가능하게 남겼다.

## 3. ★ 정정 6 — 선언값의 그림자

```python
# train_m4.py (수정 전)
ap.add_argument("--tau-kill", type=float, default=0.1)      # <- 하드코딩
...
system=SystemSpec(tau_kill=args.tau_kill, ...)

# env_sys.py -- 선언
tau_kill: float = 0.15    # 2026-07-29 재선언 (docs/42 §3)
```

CLI 기본값이 선언값을 **그림자처럼 복제**하고 있었고, 이미 갈라져 있었다.
그대로 스윕을 걸었으면 **50런 전부 미선언 값(0.1)으로 학습**된다.
`p_kill`, `r_nk` 도 같은 구조였다 (값은 우연히 일치).

수정: 세 인자의 기본값을 `None` 으로 두고 `SystemSpec()` 에서 가져온다 — 선언은
한 군데뿐이다. `P40` / `P40b` 가 대응을 강제하고, 축을 명시하면 여전히 덮어쓴다
(`--tau-kill 0.20` 은 선언된 sweep 축).

> tau_kill 0.1 은 하드킬을 **과대평가**한다. 우리에게 유리한 방향의 오차였다.

## 4. 스윕 배선 (`sweep_m4.py`)

```
축   w_kill {0, 0.25, 0.5, 0.75, 1.0} x seed {0..4} x threat_obs {on, off} = 50 런
집계 각 런의 summary.json -> hold 베이스라인(mission_eval, n=48) 대비 비교
판정 docs/46 §4.2 그대로: 무력화율과 비손실 비율을 **둘 다** 개선해야 순이득
```

`SWEEP_AXES`(omega_max · kill_radius · tau_kill)는 **1차 스윕 뒤 승자 설정 하나**에
대해서만 돌린다. 여기서 같이 돌리면 50 → 900 런이 되고, 그건 강건성 확인이 아니라
"좋은 값 찾기" 가 되어 선언 규율을 깬다.

```bash
python -m shepherd.scripts.sweep_m4 --dry-run                  # 명령 50개 출력
python -m shepherd.scripts.sweep_m4 --run --jobs 8             # 서버에서 실행
python -m shepherd.scripts.sweep_m4 --aggregate results/m4_sweep
```

### 4.1 배선 스모크

`--total-env-steps 6144` (6 업데이트) 로 끝까지 돌려 산출물을 확인했다.
학습 전이라 무력화 0.00 이 정상이고, **regime 분해는 이미 비대칭을 보인다**:

```
regime/free/captured  0.052        (FREE_CAPTURE  -- 네트 드론 단독으로도 가능한 영역)
regime/shape/captured 0.000        (SHAPING_NEEDED -- 협력이 필요한 영역)
```

경계가 학습 텔레메트리에 그대로 나타난다.

### 4.2 비용 (정직하게)

```
이 컨테이너 = 2 코어. 6144 스텝에 ~17분  ->  500k 스텝 1런 ≈ 24시간
50런 ≈ 1,200 CPU-시간
    2코어 순차   ≈ 50일     (불가)
    32코어 x16   ≈ 3일      (현실적)
```

병목은 `viability.v_shot` 이다 (`n_samples=2000` x `n_segments=4`, 스텝마다).
`n_samples` 는 `CALIBRATED` 이고 *"n-cut 은 게이트 근방에서 UNSAFE"* 로 못박혀
있으므로 **줄이지 않는다.** `total_env_steps=500k` 도 선언된 값이다
(200k 는 under-trained 로 확인됨). **줄이는 대신 병렬로 간다.**

### 4.3 ★ 판정식 정정 + 평가 프로토콜 (2026-08-01, 결과 전)

§4 에 적은 판정식 *"hold 대비 무력화율과 비손실 비율을 둘 다 개선"* 은 **성립
불가능한 조건**이었다. 두 가지 이유이고 둘 다 실측으로 확인했다.

**(1) 비손실 비율은 hold 와 비교할 수 없다.** 스크립트 기준선은 `baseline_commit=False`
라 **구조적으로 하드킬을 못 한다.** n=200 실측: `HARD_KILL 0`, 따라서
`nondestructive_frac = 1.00` 이 자명하게 참이고 어떤 정책도 이것을 '개선' 할 수 없다.

**(2) 전체 평균 무력화율이 regime 격차를 가린다.** hold 기저선 **n=500 (고정, `results/hold_baseline.json`)**:

```
전체              무력화 0.182   NET_CAPTURE 91 / PENETRATED 377 / SPENT_FAIL 32 / HARD_KILL 0
  SHAPING_NEEDED  n=297   k=0    무력화 0.000   Wilson [0.0000, 0.0128]   <- 297 판 전부 침투
  FREE_CAPTURE    n=203   k=91   무력화 0.448   Wilson [0.3815, 0.5170]
```

**45 포인트 격차**가 평균 하나(0.182)에 묻힌다. 협력이 필요하다고 **정의한** 영역에서
무개입이 297판 전부 침투당하는 것이 이 프로젝트의 핵심 대비인데, 그걸 못 보고한다.
(n=200 예비 측정에서는 0/122 · 상한 0.031 이었다. n=500 으로 상한이 0.013 까지 조여졌다.)

#### 검정력 (80%, 양측 5%)

| 기저율 | 검출 Δ | 짝X | 짝O (불일치 .33) | 짝O (불일치 .15) |
|---:|---:|---:|---:|---:|
| 0.155 (전체) | 0.05 | **923** | 1037 | 471 |
| 0.155 (전체) | 0.10 | 252 | 260 | 118 |
| **0.000 (shape)** | 0.05 | **150** | — | — |
| **0.000 (shape)** | 0.10 | **71** | — | — |

전체 지표로 Δ=0.05 를 잡으려면 런당 ~920 판이 필요하다. 짝지어도 안 줄어든다 --
페어링은 두 팔이 **공유하는 분산**을 지울 때만 이득인데 실측 불일치율이 0.33 이라
지울 것이 없다. 반면 **기저가 0 인 regime 안에서는 비교가 '알려진 상수 대비' 가 되어
6배 싸진다.**

#### 정정된 판정식 (선언)

```
1차   SHAPING_NEEDED 영역의 무력화율이 hold 기저를 유의하게 넘는가
      -> 정책의 Wilson 하한 > hold 의 Wilson 상한 (= 0.0128, n=500 에서 0/297)
2차   비손실 비율은 **w_kill 축을 따라 정책끼리** 비교한다 (단조성). hold 대비 아님

판정 통과에 필요한 최소 성공 수 (기저 상한 0.0128 기준):

    shape n=150 -> k >= 5      n=183 -> k >= 6      n=297 -> k >= 8
    즉 런당 n=300 (shape ~183) 에서 **6판 이상** 잡아야 통과한다 (약 3.3%)
```

#### 평가 프로토콜

```
hold 기저선   n=500 을 **한 번만** 측정해 results/hold_baseline.json 에 고정.
              런마다 다시 재지 않는다
런별 최종평가 n=300 (shape 약 183 판). Δ=0.05 검출에 필요한 150 판보다 여유
학습 곡선     n=20 유지 -- 곡선용이며 **판정에 쓰지 않는다** (반폭 ±0.175)
헤드라인      regime 별 보고. 전체 평균은 2차
```

`train_m4.py --final-eval-episodes 300` 이 판정용 평가를 곡선용과 분리해 수행하고
`summary.json["final_eval"]` 에 남긴다. `sweep_m4.py --aggregate` 가 위 판정식을
적용한다. P41/P42 가 판정 논리를 강제한다 (특히 **검정력 부족을 성공으로 읽지 않을 것**).

정정 방향은 1차 지표를 더 좁고 엄격하게, 2차 지표를 성립 가능하게 만드는 쪽이고,
**결과를 하나도 보기 전**이다.

### 4.4 ★ 포획 확률 곡선 — 스윕이 무엇을 이겨야 하는지가 정해졌다 (2026-08-02)

스윕 판정식(§4.3)은 `SHAPING_NEEDED` 한 칸을 상대로 세워져 있었다. 곡선을 그려 보니
**그 칸 하나로는 목표가 잘못 잡혀 있었다** (docs/45 §9):

```
                            hold (n=1500)                 intercept (n=1200)
                       네트 포획      95% Wilson       네트 포획   무력화(하드킬 포함)
EASY       a < 25.8    0.832 253/304 [0.786, 0.870]    0.807       0.840
BAND_AIM   25.8~39.3   0.010   3/292 [0.004, 0.030]    0.000       0.155   <-- ★
SHAPING    a >= 39.3   0.000   0/904 [0.000, 0.0042]   0.000       0.071
```

`SHAPING_NEEDED`(= a >= 39.3)에서 **네트로** 이기는 것은 정의상 불가능하다. 그 칸에서
얻을 수 있는 것은 하드킬뿐이고 그 대가는 비손실 포기다 -- 이건 이미 알고 있었다.
새로 보인 것은 **`BAND_AIM`** 이다. 여기는 `FREE_CAPTURE` 로 분류되지만 손튜닝
기준선이 **1.0 %** 밖에 못 잡는다 (두 배치 합산 3/518). **학습이 이길 여지가 실제로
있는 곳은 여기다.**

그리고 이 칸에서도 `intercept` 는 **15.5 %** 를 막는다 -- 전부 하드킬이고 네트 포획은
0/226 이다. 즉 `BAND_AIM` 은 "물리적으로는 네트로 잡을 수 있는데 손튜닝은 기체를
부수는 길로만 닿는" 구간이다. **학습이 이겨야 할 수는 1.0 % 가 아니라 15.5 % 이고,
그것을 비손실로 해야 한다.** 이게 이 연구의 질문 문장이다.

상한에 대한 정직한 진술: `w <= rho` 이므로 **완벽 정렬이면** 100 % 가 원리적으로
가능하지만, `omega_max` 가 유한하므로 완벽 정렬은 achievable 하지 않다. 실제 상한은
1.0 % 와 100 % 사이 어딘가이며 **그 값은 모른다**. 질문은 "학습이 그중 얼마를
회수하는가" 이지 "100 % 를 달성하는가" 가 아니다.

**판정식은 바꾸지 않는다** (결과를 본 뒤 규칙을 바꾸는 소급 변경이 된다).
대신 **집계 축을 하나 추가로 선언**한다 — 지금, 학습 결과를 보기 전에:

| 축 | 정의 | 왜 |
|---|---|---|
| `BAND_AIM` (신설, 보고용) | `a*(psi_med) <= a_att < a*` = **25.8 ~ 39.3** | 손튜닝 네트 포획 1.0 % vs 물리 요격 15.5 % — 개선 여지가 존재함이 사전 실측으로 확인된 유일한 구간 |

`BAND_AIM` 은 **1차 판정식에 들어가지 않는다.** 사전 등록된 판정은 §4.3 그대로 두고,
`BAND_AIM` 은 **함께 보고**한다. 배선도 끝냈다 (2026-08-03) — `train_m4` 의 **판정용
최종 평가와 같은 호출**에서 나오고(`summary.json` 의 `final_eval_bands`), 기저선도
같은 함수(`summarize_bands`)로 집계된다. 스윕이 끝난 뒤에 따로 뽑으면 *결과를 본 뒤
축을 만든 모양*이 되므로 그렇게 하지 않는다. P45/P45b/P45c 가 이걸 지킨다 —
특히 **P45b 는 `BAND_AIM` 이 아무리 좋아도 1차 판정이 안 바뀐다**는 것을 강제한다. 경계값 25.8 은 `slew_audit` 실측 `psi_med = 4.26 deg`
에서 나온 것이며 학습 결과와 무관하게 이미 고정돼 있다. **코드에도 못을 박았다** —
`curve_sweep.PSI_MED_DEG` / `band_of()` + P44h/P44i (선언 그림자 재발 방지).

## 7. ★ 평가 경로 결함 2건 + 프로토콜 선언 (2026-08-03, 파일럿 뒤 · 스윕 전)

파일럿 3런(500k 스텝, 5시간)의 최종 평가가 **세 런 전부 `무력화 0.000 / 침투 1.000 /
SPENT_FAIL 0`** 이었다. 그런데 같은 런의 학습 롤아웃은 `free_cap` 이 0.05 -> 0.33 으로
올라가 있었다. 두 숫자가 같은 것을 재는데 달랐고, 그 차이가 결함이었다.

### 7.1 결함 1 — 평가 경로에 `pad_env_action` 이 빠졌다

```
finisher  env Box (5,)   LIVE_DIMS (5, (0,1,2,4))    fire = env idx4,  idx3 = 예약(slew)
learned_bundle 출력 = (4,)                            패딩 없이 들어감
scripted_finisher 출력 = (5,)                         그래서 손튜닝 기준선은 멀쩡했다
```

| 경로 | 패딩 | 결과 |
|---|---|---|
| 학습 롤아웃 | `adapter.step` 이 건다 (adapter.py:90) | 정상 |
| 평가 `run_episode(policy=...)` | **없었다** | 발사 비트가 예약칸으로 -> **env 에 안 닿음** |

같은 체크포인트를 패딩만 걸고 다시 재니 **0.000 -> 0.110** (NET 11, SPENT_FAIL 0 -> 9).
`SPENT_FAIL` 이 생긴 것이 결정적 증거다 -- 그전에는 네트를 **쏜 적이 없어서** 소진될
수도 없었다.

수정: `M4Runner.policy_fn` 이 `pad_env_action` 을 건다. **P46** 이 지킨다 --
정책이 내는 행동의 모양이 env Box 와 정확히 같은지, 그리고 `env.step` 이 받는지.

### 7.2 결함 2 — 커밋 비트가 정책 손에 없다 (미해결, 다음 작업)

```python
LIVE_DIMS["limiter"] = (4, (0, 1, 2))     # reserved: pressure (idx 3)   <- M4 이전 주석
```

실측: 학습 limiter 출력은 (4대, **3**차원). env Box 는 4차원이고 **idx3 이 M4 의 커밋
비트**다 (docs/29 SS3.1). 패딩은 예약칸에 0 을 넣는다. 즉 **학습 정책은 커밋을 켤 수단이
없다** -- 학습 중에도, 평가에서도.

파일럿 세 런의 `shape_hk` 가 정확히 0 인 이유가 이것이다. 탐색이 못 찾은 것이 아니라
**하드킬이라는 행동이 정책에게 존재하지 않았다.**

**이것이 스윕의 주축을 불활성으로 만든다.** `w_kill` 은 종말 보상에만 들어간다
(`HARD_KILL = b_net*(1-w_kill)`). 하드킬이 불가능하면 `w_kill` 은 도달 불가능한 결과의
보상만 바꾼다 -- 5x5x2 스윕에서 `w_kill` 축 전체가 무의미해진다. 2차 지표(비손실 비율)도
자명하게 1.00 이 된다.

`docs/29 SS3.1` 은 처음부터 idx3 을 커밋 비트로 **선언**했다. `action_dims.py` 가 그것을
구현한 적이 없을 뿐이다. 따라서 이 수정은 선언 변경이 아니라 **선언대로의 배선**이다.

채택: `LIVE_DIMS["limiter"] -> (4, (0,1,2,3))` + limiter actor 를 `MixedActor`
(Gaussian 3 + Bernoulli 1) 로. 재학습 필요. 규칙 기반 커밋 가드(docs/29 SS15.2 폴백)는
**쓰지 않는다** -- 규칙은 근접 시 발동하므로 "비손실 선호"를 표현할 유일한 방법이
물러나는 것이 되고, 그러면 조성 능력과 비손실 축이 한 몸이 되어 우리 질문
("비손실을 지키면서 방어할 수 있는가")이 해석 불가능해진다. 커밋 차원이 학습되지
않는 것이 **실측으로** 확인되면 그때 폴백한다.

### 7.3 평가 프로토콜 선언 — 고정 시드 표본추출 (결과 보기 전)

종전 평가는 `deterministic=True` 였고, 이진 행동을 `probs > 0.5` 로 잘랐다
(mappo.py:177). 발사·커밋은 **에피소드당 한 번** 하는 행동이라 올바른 정책일수록
스텝당 확률이 낮다 -- 0.5 문턱은 그런 정책을 구조적으로 버린다. 파일럿 s1 은
`p = 0.0002` 를 배웠고 결정론 평가는 한 발도 쏘지 않았다. s0 는 반대로 `p = 0.9999`
였는데, 그 역시 패딩 결함 때문에 0 이었다.

**선언**: M4 의 판정용 평가는 **학습과 같은 분포(표본추출)** 로 하되,
`torch.manual_seed(eval_seed0)` 로 시드를 고정해 재현성을 지킨다.

* 1차 판정식(SS4.3)은 **바꾸지 않는다.** 바뀌는 것은 "학습된 정책을 어떻게 행동으로
  바꾸는가"이지 "무엇을 성공으로 세는가"가 아니다.
* 손튜닝 기준선(hold / intercept)은 정책이 없으므로 영향이 없다. 동결본 그대로 쓴다.
* **P47** 이 지킨다 -- 시드 고정 존재 + 같은 시드 두 번 호출이 같은 counts.

### 7.4 이 부류가 세 번째다

정정 3(기준선의 공짜 하드킬) · 정정 8(hold+commit == hold) · 이번 결함 1·2 는 전부
**"미사용으로 문서화된 슬롯을 새 기능이 재사용했는데 소비자 한 곳이 안 따라왔다"** 이다.
그래서 이번에는 문서가 아니라 **테스트**로 못 박는다: P46(모양 계약) · P47(프로토콜) ·
P40e(커밋 가드) · P44j(Wilson 단일 정의).
