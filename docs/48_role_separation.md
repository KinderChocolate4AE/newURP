## 1. 왜 필요한가 — 기준선이 비어 있다

파일럿(docs/47 §7)에서 학습은 `hold` 보다 나빴다. 그런데 그 사실로부터
알고리즘에 대해 말할 수 있는 것이 없다. `hold` 가 무개입이 아니기 때문이다:

```
발사 off (fire_mode="never")      무력화 0.000     <- 진짜 무개입
hold                              무력화 0.182     <- 편대는 무개입, 발사는 해석적 규칙
학습 (파일럿 3런)                 무력화 0.023~0.080
```

`hold` 의 0.182 는 **전부 발사 규칙의 성적**이다. 정적 링의 v_shot 기여도는
531 스텝 중 94.9 % 가 완전 동일하다(docs/47 §7 재검증). 그러므로

> LL < SS 는 "협력 성형을 못 배웠다" 와
> "학습된 발사 타이밍이 해석적 규칙보다 나쁘다" 를 구분하지 못한다.

두 가설은 다음 작업이 완전히 다르다. 전자면 보상·탐색(PBRS·커리큘럼)의 문제이고,
후자면 발사 헤드의 확률 붕괴(파일럿 s1 은 p=0.0002, s0 는 p=0.9999)를 먼저 잡아야
한다. 역할을 하나씩 고정하면 갈린다.

## 2. 팔 (선언)

| 팔 | limiter | finisher | 읽는 것 |
|---|---|---|---|
| **SS** | `hold` | 스크립트 (clean 임계) | 기준선. **학습 없음** — `results/hold_baseline.json` (n=500) |
| **LS** | 학습 | 스크립트 (clean 임계) | 발사를 고정했을 때 **편대 학습**의 단독 기여 |
| **SL** | `hold` | 학습 | 편대를 고정했을 때 **발사 학습**의 단독 기여 |
| **LL** | 학습 | 학습 | 결합 (= 파일럿 구성, 결함 수정 후 재측정) |

축은 이것뿐이다. `w_kill = 0.5` 로 **고정**한다 — 여기서 묻는 것은 "어느 역할이
격차를 만드는가" 이지 "어떤 보상 가중치가 좋은가" 가 아니다. 시드 {0, 1, 2, 3, 4}.

시드를 5개로 두는 이유는 검정력이 아니라 **시드 분산**이다. 파일럿에서 행동
스케일이 에피소드 0 값으로 동결돼 있었고 그 때문에 시드마다 실효 권한이
100/72/48 % 로 갈렸다 — *"기존 3시드는 복제가 아니다"* (docs/47 §7 재검증).
결함은 고쳤지만, 3개로 시드 분산을 추정하는 것은 여전히 사실상 불가능하다.
(선언 시점: 2026-08-04, 학습 결과 전.)

`SS` 를 다시 돌리지 않는 이유: 학습기를 거치지 않으므로 파일럿의 세 결함
(관측 오염·소모 벌점·행동 스케일)이 닿지 않는다. docs/47 §7 이 "기준선 두 줄은
유효하다" 고 적은 그 근거다. 스윕과 **같은 파일**을 쓰므로 두 실험의 기준선이
동일하다.

### 2.1 동결은 학습 시점이다 (평가 시점 스왑이 아니다)

이미 학습된 LL 체크포인트에서 평가 때만 finisher 를 스크립트로 바꾸는 방법도
있다. 그건 **하지 않는다**. 그 값은 "짝으로 학습된 정책을 떼어놨을 때의 조합
가능성"이지 "그 역할이 혼자 무엇을 배울 수 있는가"가 아니다. 귀속을 물으려면
각 팔이 **자기 조건에서 학습**해야 한다.

대가는 명시한다: LS 의 limiter 는 *고정된 발사 규칙을 상대로* 최적화되므로
LL 의 limiter 와 같은 문제를 푸는 것이 아니다. 그래서 §4 의 차분은 "역할의
한계 기여"가 아니라 **"그 역할만 학습시켰을 때의 도달점"** 이다. 상호작용 항을
따로 내는 것이 그 때문이다.

## 3. 배선

### 3.1 한 곳 원칙

동결된 역할의 스크립트 규칙은 기준선의 그 역할과 **같은 함수**여야 한다.
갈라지면 LS−SS 차이가 "학습의 기여"가 아니라 "두 구현의 차이"가 된다.
그래서 `mission_rollout.scripted_role_actions()` 하나만 둔다 — 기준선 경로와
동결 경로가 이것을 공유한다.

docs/47 §7.4 가 적은 대로 이 리포에서 반복된 사고(정정 3 · 정정 8 · 결함 1 ·
결함 2)는 전부 *"같은 규칙이 두 곳에 있고 소비자 한쪽이 안 따라왔다"* 였다.
이번에는 문서가 아니라 **테스트**로 못을 박는다 (§3.4).

### 3.2 두 경로에 같이 걸린다

```
학습 롤아웃   MAPPORunner.collect_rollout -> _override_live() 훅 (기본 항등)
              M4Runner 가 오버라이드해 동결 역할을 스크립트로 갈아끼운다
평가          mission_eval(scripted_roles=...) -> run_episode(scripted_roles=...)
              정책이 무엇을 내든 그 역할만 스크립트로 덮어쓴다
```

부모 `collect_rollout` 을 자식이 복사하지 않도록 **훅 두 개**(`_override_live`,
`_observe_step`)만 넣었다. 기본 구현이 항등/no-op 이므로 M2/M3/2B/2C 경로는
bit-identical (P56).

패딩 규약 주의: 스크립트는 **env Box**(limiter 4, finisher 5)를 내고
`adapter.step` 은 **LIVE** 차원을 받는다. `unpad_env_action` 이 유일한 변환
지점이다 — 다른 데서 하면 프로파일(`M4_LIVE_DIMS`)이 갈라져 결함 2 가 재발한다.

### 3.3 동결된 액터는 학습에서 뺀다

행동이 env 에 닿지 않는 액터를 그대로 학습시키면 두 경로로 오염된다:

1. `clip_grad_norm_` 이 **전역 노름**이라, 동결 액터의 grad 가 살아있는 액터의
   스텝 크기를 줄인다.
2. `target_kl` 조기중단이 두 KL 의 `max` 라, 동결 액터가 살아있는 액터의
   epoch 을 끊는다.

그래서 `MAPPOConfig.freeze_limiter / freeze_finisher` 를 두고, 동결 역할의
forward 를 `torch.no_grad()` 로 돌려 **그래프 자체를 안 만든다**. (0 을 곱하는
것만으로는 grad 텐서 0 이 생겨 Adam 의 모멘텀이 파라미터를 움직인다.)
기본값은 둘 다 `False` 이고, 그때 업데이트는 이 배선 이전과 파라미터까지
동일하다 (P55).

부수: limiter 가 동결된 팔에서 `limiter/commit_rate` 는 **제안**이지 일어난
일이 아니므로 키 이름을 `limiter/commit_rate_proposed` 로 바꾼다. 같은 키로
내면 표에서 구분되지 않는다.

## 4. 판정식 (선언 · 결과 보기 전)

1차 지표는 **바꾸지 않는다**: `SHAPING_NEEDED` 영역의 무력화율 (docs/47 §4.3).
기저는 `hold` 의 Wilson 상한 **0.0128** (n=297 에서 0/297).

```
H_lim   LS 의 Wilson 하한 > 0.0128        -> 편대 학습의 단독 순이득
H_fin   SL 의 Wilson 하한 > 0.0128        -> 발사 학습의 단독 순이득
H_syn   LL 의 하한 > max(LS 상한, SL 상한) -> 결합해야만 얻어지는 상승작용
```

**풀링 규율**: 1차 판정은 시드 풀링 Wilson 으로 한다(검정력). 풀링은 시드
분산을 0 으로 가정하므로, **시드 과반이 개별로도 기저를 넘을 때만** '강함' 으로
적는다 (5시드 → 3, 3시드 → 2). 아니면 '풀링 의존' 으로 적는다. 과반 기준은
시드 수에서 자동으로 나오게 배선했다 — 하드코딩하면 시드를 늘렸을 때 기준이
조용히 느슨해진다. 집계기가 자동으로 붙인다.

**귀속 차분**은 점추정으로만 보고하고 유의성을 주장하지 않는다:

```
limiter_only  = LS - SS
finisher_only = SL - SS
synergy       = LL - LS - SL + SS
```

**2차(보고 전용, 판정 아님)**: 전체 무력화율 · 비손실 비율 · `BAND_AIM`.
docs/47 §4.4 의 P45b 가 그대로 적용된다 — `BAND_AIM` 이 아무리 좋아도 1차
판정은 바뀌지 않는다.

**null case 도 결과다**: 세 팔 모두 기저를 못 넘으면 "어느 역할을 학습시켜도
무개입+해석적 발사를 못 넘는다" 가 결과이고, 그때 결손은 특정 역할이 아니라
학습 문제 자체에 있다 (신청서 §4.7 폴백 (v)).

### 4.1 통과에 필요한 최소 성공 수

기저 상한 0.0128 기준 (최종평가 n=300, 그중 `SHAPING` 약 183):

| 표본 | 최소 k | 비율 |
|---|---:|---:|
| 시드 1개 (n=183) | 6 | 3.28 % |
| 풀링 3시드 (n=549) | 13 | 2.37 % |
| **풀링 5시드 (n=915)** | **19** | **2.08 %** |

즉 **팔당 다섯 시드 합쳐 19판**을 잡아야 통과한다. 파일럿은 0/508 이었다.

## 5. 무엇을 답하지 못하는가

- **한계 기여가 아니다.** §2.1 대로 각 팔은 자기 조건에서 학습하므로 차분은
  "그 역할만 학습시켰을 때의 도달점" 이다. `synergy` 항이 이 비가법성을 담는다.
- **스크립트 발사 규칙은 특권적이다.** `clean_net_threshold_crossed` 는 env 가
  계산한 `v_shot` 임계 교차다. LS 는 그 신호를 공짜로 받고 SL/LL 은 관측에서
  추론해야 한다. 즉 LS 가 이기더라도 "편대 학습이 낫다" 가 아니라 **"발사 신호를
  주면 편대 학습이 통한다"** 까지만 말할 수 있다. 이건 결과 해석에 반드시 적는다.
- **3시드는 시드 분산을 재기에 적다.** 풀링 규율(§4)이 그 한계를 표기할 뿐
  없애지는 못한다.
- **SHAPING 에서 네트 포획은 정의상 불가능하다** (docs/47 §4.4). 그 칸에서
  얻을 수 있는 것은 하드킬뿐이고, 그래서 `BAND_AIM` 을 항상 같이 본다.

## 6. 실행

```bash
# 0) 기저선 (이미 있으면 건너뛴다)
python -m shepherd.scripts.sweep_m4 --baseline 500          # results/hold_baseline.json
python -m shepherd.scripts.sweep_m4 --reference 300         # results/intercept_baseline.json

# 1) 명령 9개 확인
python -m shepherd.scripts.roles_split --dry-run

# 2) 서버에서 실행 (15런은 서로 독립. OMP_NUM_THREADS=1 필수)
python -m shepherd.scripts.roles_split --run --jobs 10

# 3) 집계 (판정식이 출력에 함께 실린다)
python -m shepherd.scripts.roles_split --aggregate results/m4_roles
```

비용 (파일럿 실측 기준: 1런 4~5시간, 단일 스레드):

```
15 런 x 4.5시간 = 68 코어시간
  --jobs 10   ->  10런 동시 -> 4.5h, 남은 5런 -> 4.5h   =  약 9시간
  --jobs 15   ->  한 배치                               =  약 4.5시간
```

서버 물리코어는 24 이지만 **10 만 쓴다** (공용 기계). `--resume` 이 살아 있으므로
죽은 런은 이어서 돌릴 수 있다 — 9시간짜리 작업의 단일 실패점을 없애는 장치다.

## 7. 배선 스모크 (2048 스텝 — **결과가 아니다**)

배선이 끝까지 돌아가는지만 본 것이다. 학습이라 부를 수 없는 스텝수(선언값의
0.4 %)이고 최종평가도 n=40 이다. **인용 금지.**

| 팔 | 전체 무력화 | EASY 네트 포획 | BAND_AIM 무력화 | SHAPING |
|---|---:|---:|---:|---:|
| LL | 0.025 | 0.083 | 0.000 | 0.000 |
| **LS** | 0.275 | **0.833** | 0.143 | 0.000 |
| SL | 0.025 | 0.083 | 0.000 | 0.000 |
| (참고) SS 기저선 n=1500 | 0.182 | 0.832 | 0.010 | 0.000 |

여기서 **읽어도 되는 것은 하나뿐**이다: LS 의 EASY 네트 포획 0.833 이 기저선의
0.832 와 일치한다. limiter 가 사실상 안 배운 상태이므로 이 팔은 이 시점에
`hold` 와 같아야 하고, 실제로 같다 — **스크립트 발사 규칙이 기준선의 것과 동일
경로로 걸렸다는 증거**다 (§3.1 의 한 곳 원칙이 실제로 지켜졌다).

읽으면 안 되는 것: LL·SL 의 EASY 0.083. 학습된 발사 헤드가 초기화 직후이므로
낮은 것이 당연하다. 이것을 "발사 학습이 문제다"의 증거로 쓰면 안 된다 —
그 질문에 답하는 것은 500k 스텝 본런이다.

`commit nan` 이 SL 에서 나오는 것도 정상이다: limiter 가 동결돼 있어
`limiter/commit_rate` 대신 `..._proposed` 로 나간다 (§3.3).
